# Priority 1 — Fix Retrieval Assessment

This is the **most important change**.

Currently the assessor is effectively saying:

```text
top score is much better than the rest
        ↓
strong evidence
```

But the hardware example proves that this isn't sufficient.

It had:

```text
Top       = 0.029605
Second    = 0.003221
Mean      = 0.005153
Top/Mean  = 5.7455
```

and was nevertheless classified as:

```text
strong → generate
```



### Change

We should make retrieval assessment consider **both absolute and relative evidence**.

Instead of:

```python
if top_to_mean_ratio > X:
    strong
```

we eventually want something conceptually like:

```text
                Absolute relevance
                       +
                Relative separation
                       +
                Candidate distribution
                       ↓
                Evidence strength
```

For example:

```text
Strong:
    absolute score sufficiently high
    AND distribution is convincing

Moderate:
    reasonable evidence
    but not strongly supported

Weak:
    low absolute relevance
    regardless of relative separation
```

**Important:** I do not recommend hardcoding the exact thresholds yet. We should derive them from your observed score distributions.

# Priority 2 — Separate "relative confidence" from "evidence strength"

I recommend changing the terminology/data model slightly.

Currently you have things such as:

```text
top_score
second_score
mean_score
gap
top_to_mean_ratio
gap_ratio
evidence_strength
```

The problem is that these metrics represent different things.

I'd eventually record:

```text
absolute_relevance
relative_separation
evidence_strength
```

For example:

```json
{
    "top_score": 0.846,
    "score_gap": 0.079,
    "top_to_mean_ratio": 2.32,

    "absolute_relevance": "high",
    "relative_separation": "good",
    "evidence_strength": "strong"
}
```

versus:

```json
{
    "top_score": 0.029,
    "score_gap": 0.026,
    "top_to_mean_ratio": 5.74,

    "absolute_relevance": "low",
    "relative_separation": "excellent",
    "evidence_strength": "weak"
}
```

That second example is exactly the situation your current system mishandles.

# Priority 3 — Fix the refusal state

Currently:

```text
LLM → "I don't know."
       ↓
skip hallucination check
       ↓
normalized_grade = grounded
       ↓
record_turn
       ↓
END
```

The log explicitly shows this behavior. 

The hallucination checker skipping a refusal is fine.

**The problem is the resulting state.**

I recommend introducing a distinct state:

```text
grounded
hallucinated
refusal
```

instead of:

```text
grounded
hallucinated
```

So:

```python
hallucination_grade = "refusal"
```

rather than:

```python
hallucination_grade = "grounded"
```

when the answer is:

```text
"I don't know."
```

This will make your trace semantically correct.

# Priority 4 — Make refusal potentially recoverable

Once Priority 3 exists, the graph can distinguish:

```text

      ↓
END
```

from:

```text

      ↓

```

But **I don't recommend blindly retrying every refusal**.

We need to distinguish:

### Case A — Retrieval is weak

```text
weak retrieval
    ↓
"I don't know"
    ↓

```

### Case B — Retrieval is actually strong

```text
strong retrieval
    ↓
"I don't know"
    ↓
probably generation/model problem
```

### Case C — Document genuinely doesn't contain the answer

```text
weak evidence
    ↓
retry/rewrite
    ↓
still weak
    ↓
"I don't know"
    ↓
END
```

This is where your agentic behavior becomes meaningful.

# Priority 5 — Actually activate corrective RAG

Your graph already has the conceptual structure for this.

But the log shows that weak cases are often routed:

```text

  ↓

```

because the assessor labels them `strong`.

So corrective retrieval isn't getting enough opportunity to operate.

After Priority 1:

```text
QUERY
  ↓
RETRIEVE
  ↓
ASSESS
  ├── strong ─────→ GENERATE
  │
  ├── moderate ───→ GENERATE / optional refinement
  │
  └── weak ───────→ REWRITE

                      RETRIEVE
```

That is the change I'd consider the **core agentic-RAG improvement**.

# Priority 7 — Don't treat "generate" as synonymous with "success"

The current trace has:


# Priority 10 — Generation optimization comes later

Generation is currently:

```text
~48–52%
```

of total measured pipeline time. 

That's currently the largest single component.

But I don't recommend trying to reduce it yet.

Why?

Because your generation behavior is reasonable:

```text
~1 sec → refusal
~5–6 sec → detailed answer
```

So before optimizing it, we should implement **streaming**.

That changes the user experience dramatically without necessarily reducing backend generation time.
